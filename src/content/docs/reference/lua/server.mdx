The server-side Lua API is exposed through the global `mp` table in `.lua` files running within the `server_script` of a resource. Every resource runs in its own Lua state.

Hashes, vectors and scheduler primitives are shared with the client runtime; this page documents the server-side surface of the `mp` table.

The runtime is Lua 5.3 and also provides the globals `json` (`json.encode`, `json.decode`) and `msgpack`. Behaviour notes marked "observed" were checked by running server v4.0.4-beta.1 without a game client.

:::caution[Integers and Floats]
Lua 5.3 keeps integers (`90`) and floats (`90.0`) apart, and this API does not convert between them. A float field given an integer, or an integer field given a float, is silently ignored or stored as a meaningless value. `yaw`, `health`, `streamingRadius` and the components of a position table need floats; `dimension` needs an integer. The affected entries below say so.
:::

Several yes/no functions and fields return `1` for yes and `false` for no instead of a Lua boolean. Both work in an `if`, but `value == true` never matches `1`.

## Entity Pools

The server runtime provides five synchronized entity pools: `mp.players`, `mp.vehicles`, `mp.objects`, `mp.peds` and `mp.pickups`.

### Common Pool Methods

<a id="pool-exists"></a>

#### pool.exists(entityOrId)

> **pool.exists**(`entityOrId`): `1` | `false`

Checks whether the entity still exists. Accepts an entity object or a numeric network ID. Returns `1` when it exists and `false` otherwise.

The pool itself is not checked: any existing entity ID gives `1`, so `mp.peds.exists(vehicleId)` and `mp.players.exists(vehicleId)` are both `1` (observed). Read the entity's `type` when you need to know what the ID refers to.

<a id="pool-at"></a>

#### pool.at(entityOrId)

> **pool.at**(`entityOrId`): `Entity`

Returns the entity object. Raises `entity id is not valid` when no entity has that ID, so call `exists` first. Like `exists`, it does not check the pool: `mp.peds.at(vehicleId)` returns an object whose `type` is `2`.

<a id="pool-toarray"></a>

#### pool.toArray()

> **pool.toArray**(): `Entity[]`

Returns a Lua array with entity objects for every active entity in the pool.

<a id="pool-create"></a>

#### pool.create(options)

> **pool.create**(`options`): `Entity`

Creates a synchronized entity and returns its object. Available on vehicles, objects, peds and pickups — not on `mp.players`.

<a id="pool-destroy"></a>

#### pool.destroy(entityOrId)

> **pool.destroy**(`entityOrId`): `nil`

Removes the entity. Available on vehicles, objects, peds and pickups — not on `mp.players`. Returns nothing.

The removal takes effect on the next tick: until then `exist` still reads `1`. An unknown ID is ignored. The pool is not checked, so `mp.pickups.destroy(vehicleId)` removes the vehicle (observed).

<a id="mp-players-kick"></a>

#### mp.players.kick(playerOrId, reason)

> **mp.players.kick**(`playerOrId`, `reason`): `nil`

Disconnects the specified player. Returns nothing. An ID that is not a connected player is ignored.

## Entity Objects

An entity object is a table containing `{ id = networkId }` backed by a metatable that reads the current value from the server core on every field access. Two objects for the same entity are different tables: compare their `id`, not the objects themselves.

An object is only an ID, so it can outlive its entity. Reading a field of an entity that is gone does not raise: `exist` is `false`, `type` and `dimension` are `0`, `position` is `0, 0, 0`. IDs are reused: once a destroy has taken effect, the next `create` can return the same ID, and an object you kept then refers to the new entity (observed).

### Shared Properties (All Entities)

<a id="entity-id"></a>

#### id

> **id**: `number`

Unique network ID assigned to the entity. Treat as read-only: assigning it retargets the proxy and is not supported.

<a id="entity-type"></a>

#### type

> **type**: `number`

Entity type, read-only: `1` Player, `2` Vehicle, `3` Object, `4` Ped, `5` Pickup, `6` GameObject, `0` not found.

<a id="entity-exist"></a>

#### exist

> **exist**: `1` | `false`

`1` while the entity remains active on the server, `false` once it is gone. Read-only.

<a id="entity-position"></a>

#### position

> **position**: `vector3`

Current coordinates in Night City. Read-only.

<a id="entity-rotation"></a>

#### rotation

> **rotation**: `vector3`

Rotation, read-only: `x` roll, `y` pitch, `z` yaw.

<a id="entity-yaw"></a>

#### yaw

> **yaw**: `number`

Entity heading in degrees. Read-only.

<a id="entity-dimension"></a>

#### dimension

> **dimension**: `number`

Virtual world dimension (`0` for the default shared world). Read / write.

Assign an integer. A float is not converted: `entity.dimension = 4.0` read back as `1082130432`. Assigning `-1`, `2147483648` or `4294967295` left the value unchanged (observed).

<a id="entity-streamingradius"></a>

#### streamingRadius

> **streamingRadius**: `number`

Distance at which clients stream this entity in. Read / write. A new vehicle, ped or object reads `230.0`; a new pickup read `5.916`.

Assign a float. An integer is ignored: after `entity.streamingRadius = 50` the value is still `230.0`, while `= 50.0` works. Also observed: `0.0` is ignored, a negative value is stored as its absolute value, and a string such as `'90'` reads back as `inf`.

<a id="entity-owner"></a>

#### owner

> **owner**: `Player` | `-1` | `nil`

Player object of the network owner client, or the number `-1` when nobody owns the entity (always the case for a script-created entity while no client is connected). Read / write; assignable for non-player entities (pass a player object or network ID).

Assigning an ID that is not an existing entity raises `entity id is not valid`. That includes `-1` and `nil`, so a script cannot clear the owner this way (observed).

<a id="entity-firstowner"></a>

#### firstOwner

> **firstOwner**: `any`

Read-only. `-1` for an entity created by a script: observed on vehicles, peds, objects and pickups with no client connected. What it holds once a client has owned the entity could not be observed without a game client. Assigning it only stores a key on the Lua table.

<a id="entity-getmeta"></a>

#### entity:getMeta(key)

> **entity:getMeta**(`key`): `any`

Same as `mp.meta.getPlayer` / `mp.meta.getEntity`.

<a id="entity-setmeta"></a>

#### entity:setMeta(key, value)

> **entity:setMeta**(`key`, `value`): `nil`

Stores the value without syncing it to clients. To sync, use `mp.meta` with `sync = true`.

:::caution[Property Assignment]
Only `dimension`, `streamingRadius` and `owner` can be assigned directly on entity objects. Assigning any other property (for example `entity.position = vec`) only stores a key on the Lua table; it does not move or change the entity in the engine. Worse, that object then returns the stored key instead of the live value every time you read the field.
:::

## Hashes

REDengine identifies resources, items and appearances by 64-bit numeric hashes. The server Lua helpers return the hash as a **decimal string**; convert it with `tonumber(str, 10)` before passing it to `create` or any other API that expects a number.

<a id="mp-hashes-tocname-server"></a>

### mp.hashes.toCname(name)

> **mp.hashes.toCname**(`name`): `string`

CName hash (appearances, engine names).

<a id="mp-hashes-totweakdbid-server"></a>

### mp.hashes.toTweakdbid(name)

> **mp.hashes.toTweakdbid**(`name`): `string`

TweakDBID hash (`Vehicle.*`, `Character.*`, `Items.*`).

<a id="mp-hashes-toresref-server"></a>

### mp.hashes.toResref(path)

> **mp.hashes.toResref**(`path`): `string`

Resource reference hash (archive `.ent` paths).

<a id="mp-gethashfromname-server"></a>

### mp.getHashFromName(name, kind)

> **mp.getHashFromName**(`name`, `kind`): `string`

Same as the helpers above; `kind` is `'cname'`, `'tweakdbid'` or `'resref'`. Any other `kind` returns the string `'unknown hash type'` instead of raising, and a missing `kind` raises `native ... aborted: argument 1 is null`.

The server has no reverse `from*` helpers; they exist only on the client with `use_game_natives = true`.

:::caution[Hash Rules]
Never pass the string itself to a native or `create`: it arrives as a pointer instead of a hash. Do not hash a vehicle or ped record with `toCname`, do not hash an `.ent` path with `toTweakdbid`, and do not pass `appearance = 0` — clients can disagree on the look. Use `toTweakdbid` for vehicle, ped and pickup models, `toResref` for object models, and `toCname` for appearances.

Only pass strings to the hash helpers. Passing a number (`mp.hashes.toCname(5)`, `mp.hashes.toTweakdbid(5)`, `mp.getHashFromName(5, 'cname')`) terminated the server process in testing; `pcall` does not catch it. A missing argument raises a normal Lua error.
:::

## Creating Entities

Every `create` call returns an entity object whose `id` is assigned by the server. Options are plain Lua tables; unknown fields are ignored. The options table itself is required: `create()` raises, while `create({})` creates an entity whose model is `0`.

IDs are handed out from `65534` downward. The ID of a destroyed entity is free again as soon as the destroy has taken effect (the next tick), and the next `create` reuses it (observed).

:::caution[Position Format]
`position` must be a `vector3` or a table with named fields `x`, `y` and `z` (default `0, 0, 0`). A plain array such as `position = {-1392.6, 1271.5, 123.0}` is not read: the server reads `position.x`, `position.y` and `position.z`, so the entity is created at the origin. Always write `vector3(-1392.6, 1271.5, 123.0)` or `position = { x = -1392.6, y = 1271.5, z = 123.0 }`.

In a plain table the three components must be floats: `{ x = 1, y = 2, z = 3 }` read back as `1.4e-45, 2.8e-45, 4.2e-45`. `vector3(1, 2, 3)` converts for you and is the safer form.
:::

:::caution[Number Types in Options]
`yaw` and `health` must be floats and `dimension` must be an integer. Observed: `yaw = 90` read back as `1.26e-43` while `yaw = 90.0` read `90.0`; `health = 500` read `7.0e-43` while `health = 500.0` read `500.0`; `dimension = 2.0` read `1073741824`.
:::

## Server Events

### Registration and Triggers

<a id="mp-events-add-serverref"></a>

#### mp.events.add(name, fn)

> **mp.events.add**(`name`, `fn`): `handlerId`

Registers a listener for platform events and for custom events sent with `mp.events.trigger` from any server resource. Returns a numeric handler ID.

<a id="mp-events-remove-serverref"></a>

#### mp.events.remove(name, handlerId)

> **mp.events.remove**(`name`, `handlerId`): `nil`

Unregisters a handler registered by `add` or `addClient`. Passing the function itself does nothing; a name that was never registered raises an error. It looks for `add` handlers of that name first and only then for `addClient` handlers, so an `addClient` handler cannot be removed while an `add` handler with the same name exists.

<a id="mp-events-trigger-serverref"></a>

#### mp.events.trigger(name, ...)

> **mp.events.trigger**(`name`, `...`): `1` | `false`

Emits a local event. Returns `false` when a handler cancelled it and `1` otherwise; use `mp.events.isCanceled()` to inspect the last cancellation flag.

Observed behaviour:

- Handlers run before `trigger` returns, in every server Lua resource that registered the name, not only the calling one. They do not run in registration order.
- A handler cancels by returning exactly `false`; `nil`, `0` and `'false'` do not cancel. Every handler still runs after one of them has cancelled.
- A handler that returns `false` after an `mp.wait` is too late: `trigger` has already returned `1`.
- An error in one handler is printed to the console and does not stop the others.
- `nil` arguments are passed through and keep their position.

<a id="mp-events-addclient-serverref"></a>

#### mp.events.addClient(name, fn)

> **mp.events.addClient**(`name`, `fn`): `handlerId`

Registers a listener for network events sent by clients with `mp.events.triggerServer`. `fn` receives the sending player object as its first argument.

<a id="mp-events-addclientraw-serverref"></a>

#### mp.events.addClientRaw(name, fn)

> **mp.events.addClientRaw**(`name`, `fn`): `handlerId`

Same as `addClient`, but the first argument is the numeric player ID.

<a id="mp-events-triggerclient-serverref"></a>

#### mp.events.triggerClient(playerOrId, name, ...)

> **mp.events.triggerClient**(`playerOrId`, `name`, `...`): `number` | `false`

Sends an event to one client (`mp.events.addServer` there). Pass `-1` to broadcast to all players. Returns `false` and prints `player doesn't exists!` when given an object whose entity no longer exists.

In every other case the return value is a number with no documented meaning; it is not a delivery report. A numeric ID is not validated: `mp.events.triggerClient(999, 'evt')` returns the same kind of number although no such player exists (observed). `name` must be a string; a table or `nil` raises.

<a id="mp-events-triggerclientraw-serverref"></a>

#### mp.events.triggerClientRaw(playerId, name, ...)

> **mp.events.triggerClientRaw**(`playerId`, `name`, `...`)

Same with an explicit numeric ID.

<a id="mp-events-triggerunreliable-serverref"></a>

#### mp.events.triggerUnreliable(playerOrId, name, arg, ...)

> **mp.events.triggerUnreliable**(`playerOrId`, `name`, `arg`, `...`): `number` | `false`

Present in the runtime but not described anywhere official. It declares one more named parameter than `triggerClient`, in third position, before the variable arguments.

Observed without a game client:

- `playerOrId` is checked like in `triggerClient`: `-1` and numeric IDs are accepted, and an object whose entity does not exist prints `player doesn't exists!` and returns `false`. A non-numeric string raises `native ... aborted: invalid stoi argument`.
- `name` is handled like the name in `triggerClient`: a string or number is accepted, while a boolean, a table or `nil` raises `attempt to concatenate`.
- `arg` accepted every type tried (number, string, boolean, table) and may be omitted.
- The return value is a number with no documented meaning.

Not observable without a game client: what `arg` is for, whether it differs from the other payload values, how the event is transported, and which client function receives it.

<a id="mp-events-triggerunreliableraw-serverref"></a>

#### mp.events.triggerUnreliableRaw(playerId, name, arg, ...)

> **mp.events.triggerUnreliableRaw**(`playerId`, `name`, `arg`, `...`): `number`

Same with an explicit numeric ID. A boolean or a table as `playerId` raises `native ... aborted: invalid stoi argument` (observed). The same limits apply: nothing about delivery could be verified.

<a id="mp-events-iscanceled-serverref"></a>

#### mp.events.isCanceled()

> **mp.events.isCanceled**(): `1` | `false`

Returns `1` when the last local event was cancelled and `false` otherwise.

Handlers receive payload values as separate arguments: an array arrives as a Lua table with indexes from `1`, an object arrives as a table with named fields.

## Server Commands

<a id="mp-commands-add-serverref"></a>

### mp.commands.add(name, fn)

> **mp.commands.add**(`name`, `fn`)

Registers a console command. `fn(player, args)` is described below. Registering a name that already exists replaces its handler.

<a id="mp-commands-addraw-serverref"></a>

### mp.commands.addRaw(name, fn)

> **mp.commands.addRaw**(`name`, `fn`)

Same, but the first argument is the numeric player ID.

<a id="mp-commands-remove-serverref"></a>

### mp.commands.remove(name)

> **mp.commands.remove**(`name`)

Removes a registered command. An unknown name is ignored. The command does not have to belong to the calling resource: removing a command registered by another resource works too (observed).

<a id="mp-commands-execute-serverref"></a>

### mp.commands.execute(line)

> **mp.commands.execute**(`line`)

Runs a command registered by a resource (this one or another), with the same parsing as the console. The handler runs before `execute` returns and receives `0` as `player`, as if typed in the server terminal.

Built-in console commands cannot be run this way: `version`, `refresh`, `stop`, `max_players` and `add_var` all printed `you dont admin!` and did nothing (observed). Use `mp.resources.*` and `mp.addVar` instead. An unknown command prints `<name> command doesn't exist!`.

<a id="mp-commands-getall-serverref"></a>

### mp.commands.getAll()

> **mp.commands.getAll**(): `table`

Returns an array of command names: the built-in console commands and the commands of every resource, not only the calling one. Some built-in names appear twice.

The handler callback receives three arguments:

- `player` — the invoking player's object when the command comes from a client F8 console. When the command is typed into the **server terminal**, `player` is the **number `0`**, not `nil`; when the player no longer exists, it is the numeric player ID. Test `player == 0` and never rely on a truthiness check, because `0` is truthy in Lua.
- `args`: a Lua table of whitespace-delimited argument strings, indexed from `1`. Repeated spaces are collapsed, and double quotes group words: `say "two words" 3` gives `{ 'two words', '3' }`.
- `raw` — the full command line as typed, including the command name.

Commands run as coroutines, so `mp.wait` works inside them. All commands of a resource are removed when the resource stops.

## Entity Metadata

<a id="mp-meta-setglobal-serverref"></a>

### mp.meta.setGlobal(key, value, sync) / mp.meta.getGlobal(key)

> **mp.meta.setGlobal**(`key`, `value`, `sync`): `nil`
>
> **mp.meta.getGlobal**(`key`): `any`

Global server value. `sync = true` replicates the value to clients; an omitted `sync` means the value is kept locally. Values can be strings, numbers, booleans or tables (nested tables round-trip). A missing key reads as `nil`, and setting `nil` clears the key.

<a id="mp-meta-setplayer-serverref"></a>

### mp.meta.setPlayer(playerOrId, key, value, sync) / mp.meta.getPlayer(playerOrId, key)

> **mp.meta.setPlayer**(`playerOrId`, `key`, `value`, `sync`): `nil`
>
> **mp.meta.getPlayer**(`playerOrId`, `key`): `any`

One player.

<a id="mp-meta-setentity-serverref"></a>

### mp.meta.setEntity(entityOrId, key, value, sync) / mp.meta.getEntity(entityOrId, key)

> **mp.meta.setEntity**(`entityOrId`, `key`, `value`, `sync`): `nil`
>
> **mp.meta.getEntity**(`entityOrId`, `key`): `any`

Vehicle, ped, object or pickup. With an ID that is not an existing entity, the setters do nothing and the getters return `nil`; neither raises (observed, also for `setPlayer` / `getPlayer`).

<a id="entity-getmeta-serverref"></a>

### entity:getMeta(key) / entity:setMeta(key, value)

> **entity:getMeta**(`key`): `any`
>
> **entity:setMeta**(`key`, `value`): `nil`

Same store on the entity object. `setMeta` never syncs; the entity proxies ignore a third `setMeta` argument, so use `mp.meta.setPlayer` / `mp.meta.setEntity` with `sync = true` for keys that clients must read.

Every call to a setter fires the matching change event: `playerMetaChange(id, key, newValue, oldValue)`, `entityMetaChange(id, key, newValue, oldValue)` or `globalMetaChange(key, newValue, oldValue)`. This is not limited to synced keys, and the event also fires when the new value equals the old one, so compare `newValue` and `oldValue` yourself if you only care about real changes. `oldValue` is `nil` the first time a key is set. The event is delivered on a later tick, after the setter has returned (observed for global and entity metadata).

<a id="mp-resources-start"></a>

### mp.resources.start(name)

> **mp.resources.start**(`name`): `1` | `false`

Starts an installed resource folder. Returns `false` for an unknown name and `1` otherwise, including when the resource is already running (nothing happens then). The resource's script has run by the time the call returns.

<a id="mp-resources-stop"></a>

### mp.resources.stop(name)

> **mp.resources.stop**(`name`): `1` | `false`

Stops an active resource. Returns `false` for an unknown name and `1` otherwise, including when the resource was already stopped. The resource's `resourceStop` handlers have run by the time the call returns.

<a id="mp-resources-restart"></a>

### mp.resources.restart(name)

> **mp.resources.restart**(`name`): `1` | `false`

Stops and starts an active resource. Returns `false` for an unknown name and `1` otherwise. A resource that is currently stopped is simply started.

<a id="mp-resources-refreshall"></a>

### mp.resources.refreshAll()

> **mp.resources.refreshAll**()

Rescans the resources folder, like the `refresh` console command, and fires `resourcesRefresh`. Returned `false` in testing; do not use the return value.

<a id="mp-resources-getstate"></a>

### mp.resources.getState(name)

> **mp.resources.getState**(`name`): `number`

`0` only for a name the server does not know, `1` starting, `2` started, `3` stopped or found but never started. A resource reads `1` for itself while its script file is being run at start, and `2` afterwards. The built-in core resource is named `cybermp_core`.

<a id="mp-resources-gettomlfile"></a>

### mp.resources.getTomlFile(name)

> **mp.resources.getTomlFile**(`name`): `string` | `nil`

The resource's `resource.toml` as a JSON string; works for a resource that was never started. `nil` for an unknown name.

<a id="mp-resources-loadfile"></a>

### mp.resources.loadFile(name, path)

> **mp.resources.loadFile**(`name`, `path`): `string` | `nil`

Content of a file inside that resource, as a string. `nil` when the resource or the file does not exist.

<a id="mp-resources-getcurrentname"></a>

### mp.resources.getCurrentName()

> **mp.resources.getCurrentName**(): `string`

Name of the current resource.

Stopping or restarting a resource closes its Lua state: event handlers, tasks, timeouts and `mp.onUpdateLoop` callbacks of the old instance are gone, and its commands are removed. Entities created with `mp.*.create` stay on the server, so destroy them in a `resourceStop` handler if they belong to the resource. After editing `resource.toml`, run `refresh` (or `refreshAll`) before `start`/`restart`, because restart does not reread the manifest.

## HTTP Requests

<a id="mp-sendhttprequest"></a>

### mp.sendHttpRequest(url, callback, method, data, headers, options)

> **mp.sendHttpRequest**(`url`, `callback`, `method`, `data`, `headers`, `options`)

- `url` — request address.
- `callback`: `function(status, body, headers, err)`. It runs later as a coroutine, so `mp.wait` works inside it. The three possible outcomes are listed below.
- `method`: HTTP method string; defaults to `'GET'`. It is sent as written, so use upper case: `'post'` reached the test server as an invalid method.
- `data`: request body string (pass an encoded string such as `json.encode(t)`; a table raises `bad cast`). Without a `Content-Type` header the body is sent as `application/x-www-form-urlencoded`.
- `headers` — table of header names to values.
- `options`: optional table; the supported field is `followRedirects` (boolean, default `true`). With `false`, a redirect is returned as is (`302`, with its body and `Location` header).

The function returns nothing. What the callback receives (observed):

| Outcome | `status` | `body` | `headers` | `err` |
| :--- | :--- | :--- | :--- | :--- |
| Response with a status below `400` | HTTP code | response string (`''` when empty) | table of response headers | `nil` |
| Response with status `400` or above | HTTP code | `nil` | empty table | `'HTTP <code>: <response body>'` |
| No response (connection refused, bad URL) | `0` | `nil` | empty table | text starting with `Error in curl:` |

A header sent several times (`Set-Cookie`) arrives as an array of strings. On an error status the response body is only available inside `err`.

There is no timeout option: a request to a test server that accepted the connection and never answered had still not called back after 5 seconds, with or without `timeout` in `options`. A refused connection took about 2 seconds to report.

### Script Scheduling

<a id="mp-spawntask-serverref"></a>

#### mp.spawnTask(fn)

> **mp.spawnTask**(`fn`): `nil`

Runs `fn` as a coroutine on the next scheduler pass.

<a id="mp-spawntaskimmediatly-serverref"></a>

#### mp.spawnTaskImmediatly(fn)

> **mp.spawnTaskImmediatly**(`fn`): `boolean`

Runs `fn` as a coroutine immediately, up to its first `mp.wait`. The name is spelled this way in the API. Returns `true`, or `false` when `fn` raised an error before its first wait (the error is printed).

<a id="mp-wait-serverref"></a>

#### mp.wait(ms)

> **mp.wait**(`ms`): `nil`

Suspends the current coroutine for `ms` milliseconds. `mp.wait(0)` resumes on the next pass, which came 50 ms later on an idle server.

<a id="mp-settimeout-serverref"></a>

#### mp.setTimeout(fn, ms)

> **mp.setTimeout**(`fn`, `ms`): `nil`

Runs `fn` as a coroutine after `ms` milliseconds. Returns nothing and cannot be cancelled.

<a id="mp-onupdateloop-serverref"></a>

#### mp.onUpdateLoop(fn)

> **mp.onUpdateLoop**(`fn`): `nil`

Calls `fn` on every script tick. There is no way to remove it. On an idle server it ran 18 times in about one second.

`mp.wait` works only inside a coroutine; event handlers, command handlers, tasks, timeouts and HTTP callbacks are coroutines, while the main body of a script file is not. Calling `mp.wait` there raises `attempt to yield from outside a coroutine`: wrap the code in `mp.spawnTask`.

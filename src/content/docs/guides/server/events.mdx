Almost everything your server script does starts with an event. The server tells you when something happens (a player connects, someone takes damage, a vehicle spawns), clients send you their own events, and you send events back to them. All of it goes through `mp.events`.

| You want to… | JS | Lua |
| :--- | :--- | :--- |
| Listen to a built-in or custom server event | `mp.events.on` | `mp.events.add` |
| Fire a custom event on the server | `mp.events.emit` | `mp.events.trigger` |
| Listen to an event sent by a client | `mp.events.onClient` | `mp.events.addClient` |
| Send an event to a client | `mp.events.emitClient` / `player.emit` | `mp.events.triggerClient` / `player:trigger` |
| Stop listening | `mp.events.off` | `mp.events.remove` |

## Platform and custom events

*Platform events* are the ones the server fires by itself: `playerConnected`, `playerDeath`, `vehicleSpawn`, `resourceStop` and so on. The full list with argument types is in the [`MpEventsMap`](/reference/server/api/events/mpeventsmap/) reference (JS) and the [Lua event catalog](/reference/lua/server/#platform-event-catalog).

*Custom events* are names you make up. `mp.events.emit` (`trigger` in Lua) fires one on the server, and every handler registered for that name runs, including handlers in other server resources, which makes custom events a simple way for resources to talk to each other.

<Tabs syncKey={SCRIPT_LANG_TAB_SYNC_KEY}>
  <TabItem label="JS">
    ```js title="server.js"
    // Platform event: a player finished connecting
    mp.events.on('playerConnected', (playerId, tempId) => {
      console.log(`Player connected with network ID ${playerId}`);
    });

    // Platform event: a player died
    mp.events.on('playerDeath', (playerId, data) => {
      if (data.killerId) {
        console.log(`Player ${playerId} was flatlined by player ${data.killerId}`);
      } else {
        console.log(`Player ${playerId} died`);
      }
    });

    // Custom event: the name and arguments are up to you
    mp.events.on('logServerActivity', (action, details) => {
      console.log(`[Activity] ${action}: ${details}`);
    });

    mp.events.emit('logServerActivity', 'Database', 'Connection established');
    ```
  </TabItem>
  <TabItem label="Lua">
    ```lua title="server.lua"
    -- Platform event: a player finished connecting
    mp.events.add('playerConnected', function(playerId, tempId)
      print(string.format("Player connected with network ID %s", playerId))
    end)

    -- Platform event: a player died
    mp.events.add('playerDeath', function(playerId, data)
      if data.killerId then
        print(string.format("Player %s was flatlined by player %s", playerId, data.killerId))
      else
        print(string.format("Player %s died", playerId))
      end
    end)

    -- Custom event: the name and arguments are up to you
    mp.events.add('logServerActivity', function(action, details)
      print(string.format("[Activity] %s: %s", action, details))
    end)

    mp.events.trigger('logServerActivity', 'Database', 'Connection established')
    ```
  </TabItem>
</Tabs>

:::note[Events give you IDs, not objects]
Platform events pass numeric IDs. Turn an ID into an object with `mp.players.at(id)` (or `mp.vehicles.at`, …), and check `mp.players.exists(id)` first when the player might have left: for a missing player, `at()` returns `undefined` in JS and raises an error in Lua.
:::

## Receiving events from clients

A client script sends an event with `mp.events.emitServer` (`triggerServer` in Lua). On the server you catch it with `onClient` (`addClient` in Lua). The first argument of your handler is always the **player object** of the sender, added by the server; the arguments the client sent come after it.

<Tabs syncKey={SCRIPT_LANG_TAB_SYNC_KEY}>
  <TabItem label="JS">
    ```js title="server.js"
    mp.events.onClient('requestVehicleSpawn', (player, modelName) => {
      console.log(`${player.nickname} (${player.id}) asked for a vehicle: ${modelName}`);

      // Validate the request, then create the vehicle here
    });
    ```
  </TabItem>
  <TabItem label="Lua">
    ```lua title="server.lua"
    mp.events.addClient('requestVehicleSpawn', function(player, modelName)
      print(string.format("%s (%s) asked for a vehicle: %s", player.nickname, player.id, modelName))

      -- Validate the request, then create the vehicle here
    end)
    ```
  </TabItem>
</Tabs>

:::caution[Don't trust what the client sends]
You can rely on `player`, because the server sets it. Everything after it comes from the player's machine and can be forged: check types, ranges and permissions before acting on it.
:::

The client side of this exchange is covered in [client events](/guides/client/events/#communicating-with-the-server).

### Example: validating a client request

Here a client asks to lock or unlock a vehicle by sending its ID. Before doing anything, the server checks three things: that the argument really is the ID of an existing vehicle, that the vehicle belongs to the sender, and that the sender is standing next to it.

The owner is read from an `ownerId` value that your own code stored on the vehicle when it spawned it, with [entity metadata](/guides/server/meta/#entity-metadata-vehicles-peds-objects-pickups).

<Tabs syncKey={SCRIPT_LANG_TAB_SYNC_KEY}>
  <TabItem label="JS">
    ```js title="server.js"
    const MAX_LOCK_DISTANCE = 5; // meters

    // Positions are arrays: [x, y, z]
    function distanceBetween(positionA, positionB) {
      const dx = positionA[0] - positionB[0];
      const dy = positionA[1] - positionB[1];
      const dz = positionA[2] - positionB[2];
      return Math.sqrt(dx * dx + dy * dy + dz * dz);
    }

    mp.events.onClient('vehicle:toggleLock', (player, vehicleId) => {
      // The client can send anything here: text, nothing at all, a made-up ID.
      if (typeof vehicleId !== 'number' || !mp.vehicles.exists(vehicleId)) {
        return;
      }

      const vehicle = mp.vehicles.at(vehicleId);

      if (vehicle.getMeta('ownerId') !== player.id) {
        player.emit('chat:add', 'This is not your vehicle.');
        return;
      }

      // Same dimension and close enough, measured with the positions the server knows.
      const isNearby =
        vehicle.dimension === player.dimension &&
        distanceBetween(player.position, vehicle.position) <= MAX_LOCK_DISTANCE;
      if (!isNearby) {
        player.emit('chat:add', 'You are too far from the vehicle.');
        return;
      }

      const isLocked = vehicle.getMeta('isLocked') === true;
      vehicle.setMeta('isLocked', !isLocked, true);
    });
    ```
  </TabItem>
  <TabItem label="Lua">
    ```lua title="server.lua"
    local MAX_LOCK_DISTANCE = 5 -- meters

    -- Positions are indexed from 1: x, y, z
    local function distanceBetween(positionA, positionB)
      local dx = positionA[1] - positionB[1]
      local dy = positionA[2] - positionB[2]
      local dz = positionA[3] - positionB[3]
      return math.sqrt(dx * dx + dy * dy + dz * dz)
    end

    mp.events.addClient('vehicle:toggleLock', function(player, vehicleId)
      -- The client can send anything here: text, nothing at all, a made-up ID.
      if type(vehicleId) ~= 'number' or not mp.vehicles.exists(vehicleId) then
        return
      end

      local vehicle = mp.vehicles.at(vehicleId)

      if vehicle:getMeta('ownerId') ~= player.id then
        player:trigger('chat:add', 'This is not your vehicle.')
        return
      end

      -- Same dimension and close enough, measured with the positions the server knows.
      local isNearby =
        vehicle.dimension == player.dimension and
        distanceBetween(player.position, vehicle.position) <= MAX_LOCK_DISTANCE
      if not isNearby then
        player:trigger('chat:add', 'You are too far from the vehicle.')
        return
      end

      local isLocked = vehicle:getMeta('isLocked') == true
      mp.meta.setEntity(vehicle, 'isLocked', not isLocked, true)
    end)
    ```
  </TabItem>
</Tabs>

What to take from it:

- Never let the client tell you who it is or where it is. `player` comes from the server, and so do `player.position` and `vehicle.position`.
- Reject bad input quietly. A wrong type usually means a bug or someone poking at your events, and neither needs a friendly message.
- `isLocked` is only a synced value. The door does not lock by itself: a client script has to read the value and act on it. `chat:add` is likewise a custom event that your client script must handle.
- A player can send the same event hundreds of times per second. If a handler does something expensive (a database query, spawning an entity), remember when each player last used it and ignore requests that come too fast.

## Sending events to clients

There are two equivalent ways to send an event to one player:

- `mp.events.emitClient(player, 'name', ...args)` in JS, `mp.events.triggerClient(player, 'name', ...)` in Lua. `player` can be a player object or a numeric ID.
- `player.emit('name', ...args)` in JS, `player:trigger('name', ...)` in Lua, when you already have the player object.

The client receives it with `mp.events.onServer` (`addServer` in Lua). Nothing happens on the client unless one of your client scripts listens for that name.

<Tabs syncKey={SCRIPT_LANG_TAB_SYNC_KEY}>
  <TabItem label="JS">
    ```js title="server.js"
    // With the ID, which is what platform events give you
    mp.events.on('playerSpawn', (playerId) => {
      mp.events.emitClient(playerId, 'serverNotification', 'Welcome back to Night City.');
    });

    // With the player object
    function warnPlayer(player) {
      player.emit('serverNotification', 'Watch your driving, choom.');
    }

    // To reach everyone, loop over the connected players
    function notifyAll(message) {
      for (const player of mp.players.toArray()) {
        player.emit('serverNotification', message);
      }
    }
    ```
  </TabItem>
  <TabItem label="Lua">
    ```lua title="server.lua"
    -- With the ID, which is what platform events give you
    mp.events.add('playerSpawn', function(playerId)
      mp.events.triggerClient(playerId, 'serverNotification', 'Welcome back to Night City.')
    end)

    -- With the player object
    function warnPlayer(player)
      player:trigger('serverNotification', 'Watch your driving, choom.')
    end

    -- To reach everyone, loop over the connected players
    function notifyAll(message)
      for _, player in ipairs(mp.players.toArray()) do
        player:trigger('serverNotification', message)
      end
    end
    ```
  </TabItem>
</Tabs>

Sending to a player who has just left is harmless: in JS, `mp.events.emitClient` with an ID that is no longer connected does nothing.

## Cancelling platform events

Some platform events fire *before* the action takes effect, and let you veto it: return `false` from the handler and the action is cancelled. That is how you block damage, for example.

:::note
Older examples call `mp.cancelEvent()`. That function no longer exists; returning `false` is the way to cancel.
:::

### Example: a safe zone

This blocks all damage to players standing inside a circle around a given point. It reuses the `distanceBetween` helper from the [example above](#example-validating-a-client-request).

<Tabs syncKey={SCRIPT_LANG_TAB_SYNC_KEY}>
  <TabItem label="JS">
    ```js title="server.js"
    const SAFE_ZONE_CENTER = [-1456.8, 1038.2, 16.8];
    const SAFE_ZONE_RADIUS = 30; // meters

    function isInSafeZone(position) {
      return distanceBetween(position, SAFE_ZONE_CENTER) <= SAFE_ZONE_RADIUS;
    }

    // In `damage`, the first argument is the attacker; the victim is data.victimId.
    mp.events.on('damage', (attackerId, data) => {
      if (!mp.players.exists(data.victimId)) return;

      const victim = mp.players.at(data.victimId);
      if (isInSafeZone(victim.position)) {
        // Returning false cancels the damage.
        return false;
      }
    });
    ```
  </TabItem>
  <TabItem label="Lua">
    ```lua title="server.lua"
    local SAFE_ZONE_CENTER = vector3(-1456.8, 1038.2, 16.8)
    local SAFE_ZONE_RADIUS = 30 -- meters

    local function isInSafeZone(position)
      return distanceBetween(position, SAFE_ZONE_CENTER) <= SAFE_ZONE_RADIUS
    end

    -- In `damage`, the first argument is the attacker; the victim is data.victimId.
    mp.events.add('damage', function(attackerId, data)
      if not mp.players.exists(data.victimId) then return end

      local victim = mp.players.at(data.victimId)
      if isInSafeZone(victim.position) then
        -- Returning false cancels the damage.
        return false
      end
    end)
    ```
  </TabItem>
</Tabs>

Only an explicit `false` cancels. Returning nothing lets the action through, so a handler that just logs never blocks anything. The `damage` handler runs for every hit on the server, so keep it cheap: a distance check is fine, a database query is not.

Not every event can be cancelled. In the JS typings, the cancellable ones are those whose handler is typed as returning `void | boolean`:

| Group | Cancellable events |
| :--- | :--- |
| Players | `damage`, `meleeAction`, `shootAction`, `weaponReload`, `throwGrenade`, `playerHealing`, `playerKnockdown`, `playerAppearanceChange` |
| Vehicles | `vehicleWeaponShoot`, `vehicleHittedByPlayer` |
| Pickups | `pickupChange`, `pickupRaise`, `pickupDrop` |
| World | `doorStateChange`, `liftStateChange`, `fire`, `explosion` |

For Lua, the [event catalog](/reference/lua/server/#platform-event-catalog) says for each event whether it is cancellable.

## Removing handlers

Remove a handler when you no longer need it, for example a temporary listener used during a mission.

- In JS, pass the **same function** you registered to `mp.events.off`. That means you need to keep a reference to it: an inline arrow function cannot be removed.
- In Lua, `mp.events.add` returns a handler ID; pass that ID to `mp.events.remove`.

Both also work for handlers registered with `onClient` / `addClient`.

<Tabs syncKey={SCRIPT_LANG_TAB_SYNC_KEY}>
  <TabItem label="JS">
    ```js title="server.js"
    const trackExplosions = (playerId, data) => {
      console.log(`Explosion at [${data.posX}, ${data.posY}, ${data.posZ}]`);
    };

    mp.events.on('explosion', trackExplosions);

    // Later, when you no longer need it
    mp.events.off('explosion', trackExplosions);
    ```
  </TabItem>
  <TabItem label="Lua">
    ```lua title="server.lua"
    local function trackExplosions(playerId, data)
      print(string.format("Explosion at [%s, %s, %s]", data.posX, data.posY, data.posZ))
    end

    local explosionHandler = mp.events.add('explosion', trackExplosions)

    -- Later, when you no longer need it
    mp.events.remove('explosion', explosionHandler)
    ```
  </TabItem>
</Tabs>

## How handlers run

A few rules that matter once a server has more than a handful of handlers:

- **Several handlers per event are fine.** They run in the order they were registered.
- **An error in one handler does not stop the others.** The server logs it (``[Error] error in event `name': …``) and moves on to the next handler.
- **`emit` is synchronous.** `mp.events.emit` (`trigger` in Lua) runs every handler before it returns, in every server resource, whether that resource is written in JS or Lua.
- **Only Lua tells you about cancellation of custom events.** `mp.events.trigger` returns `false` when one of the handlers returned `false`. In JS, `mp.events.emit` returns nothing.
- **Handlers belong to their resource.** When a resource stops or restarts, its handlers are removed with it. You only need `off` / `remove` for handlers you want to drop while the resource keeps running.
- **Spawn and metadata events arrive a moment later.** Events such as `vehicleSpawn`, `vehicleDespawn` and `entityMetaChange` fire shortly after the call that caused them, not during it.

## Reaching the browser UI (CEF)

CEF (Chromium Embedded Framework) is the embedded browser that draws your HTML interface on the player's screen. It runs inside the client, so the server cannot send an event to it directly. The message has to go through a client script, which passes it on:

<Tabs syncKey={SCRIPT_LANG_TAB_SYNC_KEY}>
  <TabItem label="JS">
    ```js title="server.js"
    function sendInventory(player) {
      const inventory = [
        { item: 'Katana', count: 1 },
        { item: 'MaxDoc', count: 3 },
      ];

      player.emit('browser:updateInventory', inventory);
    }
    ```

    ```js title="client.js"
    // The client only passes the data on to the page.
    mp.events.onServer('browser:updateInventory', (inventory) => {
      mp.events.emitCef('updateInventory', inventory);
    });
    ```
  </TabItem>
  <TabItem label="Lua">
    ```lua title="server.lua"
    function sendInventory(player)
      local inventory = {
        { item = 'Katana', count = 1 },
        { item = 'MaxDoc', count = 3 },
      }

      player:trigger('browser:updateInventory', inventory)
    end
    ```

    ```lua title="client.lua"
    -- The client only passes the data on to the page.
    mp.events.addServer('browser:updateInventory', function(inventory)
      mp.events.triggerCef('updateInventory', inventory)
    end)
    ```
  </TabItem>
</Tabs>

The client half is explained in [Interacting with CEF](/guides/client/events/#interacting-with-cef-browser-ui).

:::tip
Writing a forwarding handler on the client for every UI message gets repetitive. The [RPC packages](/guides/recipes/rpc/) remove that step: the server and the browser can call each other directly and `await` a result.
:::
